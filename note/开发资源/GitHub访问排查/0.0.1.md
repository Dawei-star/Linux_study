# GitHub 间歇性无法访问的排查与修复（hosts 固定官方节点）

> 版本：0.0.1（首次沉淀）
> 日期：2026-10-20
> 状态：已完成
> 环境：Lenovo Legion Y7000P IRH8 / Ubuntu 26.10 / kernel 7.3.0-9-generic / Wi-Fi `wlp0s20f3`
> 一句话结论：`github.com` 被解析到 443 不通的官方边缘 IP `20.205.243.166`；在 `/etc/hosts` 固定到可用的官方边缘 `20.27.177.113` 后，主站恢复 `200 OK`。`raw.githubusercontent.com` 和 `gist.github.com` 仍未恢复。

---

## 1. 结论摘要

- 故障不是 DNS 解析失败，也不是本机代理问题，而是解析到的 GitHub 边缘 IP 的 443 端口不可达。
- 同一时刻，`api.github.com`、`codeload.github.com`、GitHub 静态资源域名均可访问，说明不是整条外网中断。
- 多个 GitHub 官方 IP 可正常完成 TLS 1.3 握手；`20.27.177.113` 延迟最低，5 次握手平均 290ms。
- 最终采用 `/etc/hosts` 固定 `github.com`、`www.github.com` 到 `20.27.177.113`，未使用 VPN、代理或第三方加速器，修改可回滚。
- 遗留限制：`raw.githubusercontent.com`、`gist.github.com` 属于不同域名，本方案未覆盖。

---

## 2. 背景与目标

### 2.1 背景

- 需要在浏览器中正常访问 `github.com`，查看仓库、登录和下载 Release。
- 当天出现间歇性故障：曾短暂恢复 `200 OK`，随后再次超时，重复性差。
- 使用者明确要求不使用 VPN/代理类工具，优先免费、可验证、可回滚的方案。

### 2.2 目标

1. 在当前 Wi-Fi 下恢复 `github.com` 的浏览器访问。
2. 不安装常驻代理软件，不转发流量，不改变系统全局网络出口。
3. 修改可回滚，且不影响除 `github.com` 之外的其他域名。
4. 记录判断依据，便于 GitHub 更换边缘 IP 后快速复测。

### 2.3 非目标

- 不解决 `raw.githubusercontent.com`、`gist.github.com` 的访问；它们不属于同一条解析路径。
- 不引入免费公共加速器、公共镜像或第三方代理。
- 不处理 git/curl 未安装的问题；本次目标是浏览器访问。排查使用 `wget`、`python3`、`dig`。

---

## 3. 排查过程与关键证据

### 3.1 故障时的表现（2026-10-20 16:58 CST）

| 检查项 | 结果 | 说明 |
|---|---|---|
| DNS 解析 `github.com` | `20.205.243.166` | 能正常解析，不是解析失败 |
| ICMP `ping github.com` | 2 发 2 收，平均 487.7ms | IP 层可达 |
| TCP 443 `github.com` | `TimeoutError` | HTTPS 实际不可用 |
| `api.github.com` | `20.205.243.168`，HTTP 200，TLS 1.3，207ms | 其他 GitHub API 正常 |
| `codeload.github.com` | `20.205.243.165`，HTTP 301 | 源码归档链路可连 |
| `raw.githubusercontent.com` | `185.199.109.133`，连接被重置 | 4 个候选 IP 均被重置 |
| `gist.github.com` | 解析到 `159.106.121.75`，HTTPS 失败 | 与主站不同链路 |
| GitHub 静态资源域名 | `github.githubassets.com`、`avatars.githubusercontent.com` 等可建立 HTTPS 连接 | 页面资源链路基本正常 |

### 3.2 官方节点验证

| 官方 IP | HTTPS 结果 | 延迟 |
|---|---|---|
| `140.82.113.3` | 页面返回 200，证书 `CN=github.com` | 5 次 TLS 握手平均 632ms |
| `20.27.177.113` | 页面返回 200，证书有效 | 5 次 TLS 握手平均 290ms（254–341ms） |
| `140.82.112.3` / `140.82.114.3` / `140.82.121.3` / `20.201.28.151` | 可完成 TLS 握手并返回 200 | 单次测试均可用，未逐一取平均 |

- 反向解析：`20.205.243.166 → github.com.`，`20.27.177.113 → www.github.com.`，PTR 均为 GitHub 域名。
- 通过 `20.27.177.113` 访问时，TLS 证书校验通过，排除证书问题。
- `/etc/nsswitch.conf` 为 `hosts: files mdns4_minimal [NOTFOUND=return] dns`，`/etc/hosts` 优先于 DNS 查询。
- 系统无 `http_proxy`/`https_proxy` 环境变量，GNOME 代理模式为 `none`，也没有常见代理端口在监听；没有 IPv6 默认路由。可排除本机代理配置导致。
- 故障会反复：同一域名可能被分配到不同边缘 IP，或同一 IP 的链路状态变化。16:58 时 `20.205.243.166:443` 超时，其它官方 IP 正常；仅清浏览器缓存或重试无法稳定解决。

## 4. 方案对比

| 方案 | 做法 | 优点 | 成本/风险 | 结论 |
|---|---|---|---|---|
| A. hosts 固定官方节点 | 将 `github.com`、`www.github.com` 固定到 `20.27.177.113` | 免费、立即生效、无代理进程、可回滚、延迟最低 | GitHub 更换 IP 后需更新；只覆盖 `github.com`；跳过 DNS 的区域选点 | 采用 |
| B. 换网络/手机热点 | 切换到另一条合法网络后重试 | 不改系统、最符合“不使用代理”的约束 | 需要额外网络；新网络也可能解析到不可用节点；不可复现 | 未采用 |
| C. 官方只读入口 | 使用 `vscode.dev` 或 `api.github.com` 浏览 | 免费、官方、无需改系统 | 不是完整 GitHub；登录、Issues、PR 等功能不可用；`raw` 仍不可达 | 作为临时备选 |
| D. 免费公共加速器/镜像 | 使用第三方 GitHub 加速站点 | 表面上免费、使用简单 | 与“不使用代理/加速器”的约束冲突；存在隐私、劫持和可用性风险 | 否决 |
| E. 等待/反复重试 | 不做修改，等待链路恢复 | 零改动 | 恢复时间不可控，故障会反复 | 否决 |

---

## 5. 取舍理由

1. **优先修复明确的单点故障**：ICMP 可达但 443 超时，说明不是整条网络断开；固定一个已验证的官方 IP 是最小改动。
2. **选择 `20.27.177.113` 而不是 `140.82.113.3`**：前者 5 次 TLS 握手平均 290ms，后者平均 632ms；两者都能返回 200，前者体验更好。
3. **不选换网络或公共加速器**：换网络最符合“零改动”偏好，但无法保证新网络解析结果更好；公共加速器违反使用者的合规约束，并有第三方信任风险。
4. **前提条件**：当前网络对部分 GitHub 边缘 IP 不稳定。如果网络环境变化，或 GitHub 调整 IP，应重新测试并按需移除/更新 hosts 记录。

## 6. 已执行操作

由使用者在终端执行，已确认备份存在：

```bash
# 1. 备份，实际生成 /etc/hosts.bak.20261020-170253
sudo cp -a /etc/hosts /etc/hosts.bak.$(date +%Y%m%d-%H%M%S)

# 2. 追加固定解析
printf '\n# GitHub direct edge\n20.27.177.113 github.com www.github.com\n' | sudo tee -a /etc/hosts

# 3. 刷新 DNS 缓存
sudo resolvectl flush-caches
```

执行后完全关闭并重新打开浏览器。

## 8. 回滚方式

优先恢复备份：

```bash
sudo cp -a /etc/hosts.bak.20261020-170253 /etc/hosts
sudo resolvectl flush-caches
```

或只删除新增的两行：

```bash
sudo sed -i '/# GitHub direct edge/d; /20\.27\.177\.113 github\.com/d' /etc/hosts
sudo resolvectl flush-caches
```

操作后重启浏览器。

## 9. 后续与未决事项

- **`raw` / `gist` 仍不可用**：网页 “Raw” 会失败，gist 也无法打开。可改用 **Download ZIP**、Releases 资源，或通过 `https://api.github.com/repos/<owner>/<repo>/contents/<path>` 获取文件内容；gist 若必须使用，需要单独寻找官方链路或更换网络。
- **IP 轮换维护**：GitHub 可能更换边缘 IP。若 `github.com` 再次失败，先用 `getent ahostsv4 github.com` 和 `wget https://github.com` 复测，再从已验证的官方 IP 中选择可用节点更新 hosts；不要使用来源不明的第三方 IP。
- **网络变化时重新评估**：如果更换 Wi-Fi 或使用手机热点，当前固定 IP 可能不再是最优选择，可先移除 hosts 记录再测试。
- **合规边界**：本方案只修改域名解析，不建立隧道、不转发流量、不安装代理软件；是否继续使用由使用者在自身合规要求下判断。若判定不可接受，按第 8 节回滚并改用其他网络。
