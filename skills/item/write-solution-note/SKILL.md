# 沉淀解决方案笔记

## 何时使用

- 一次排障、系统操作或开发任务已经完成，需要留存结论与依据；
- 比较过多个方案并做出选择，需要记录为什么这样选；
- 用户要求「总结 / 整理 / 复盘 / 沉淀 / 记一下」。

不用于：纯操作手册（不含决策）、临时草稿、需要保留完整日志的场景。

## 输出位置

先查看 `/home/bot/项目/other/note` 的现有结构再决定路径：

- 默认：`/home/bot/项目/other/note/有用的知识/<主题>/0.0.1.md`
- 主题属于已有大类时放进对应目录：`操作系统/<主题>/0.0.1.md`、`开发资源/<主题>/0.0.1.md`
- 目录名用中文短主题，如 `EFI启动项清理`、`登录限流方案`
- 已存在同主题文件时：读取上一版，另存为下一版本（`0.0.2`、`0.0.3`…），在头部注明「本版变化」，不要覆盖旧版
- 改动尚未执行时状态标为「待执行」，执行并验证后标为「已完成」

## 文档模板

```markdown
# <主题>

> 版本：0.0.1
> 日期：YYYY-MM-DD
> 状态：已完成 / 待执行 / 待评审
> 环境：<机器型号 / 项目 / 系统版本>
> 一句话结论：<最终采用了什么，解决了什么>

---

## 1. 结论摘要

3–5 行。先说结果和关键前提，不铺垫过程。

## 2. 背景与目标

- 为什么会遇到这个问题 / 为什么要做这件事
- 目标与约束（稳定优先、时间、不可逆风险等）
- 明确不做什么

## 3. 方案对比

| 方案 | 做法 | 优点 | 成本/风险 | 结论 |
|---|---|---|---|---|
| A | ... | ... | ... | 采用 |
| B | ... | ... | ... | 否决 |

至少列出两个真实考虑过的方案；只有一个可行方案时，用「不做」或「维持现状」作为对照。

## 4. 取舍理由

- 关键判据（可验证的事实、证据）
- 放弃其他方案的具体原因，不写「感觉更好」
- 方案的前提条件，以及前提变化时该怎么选

## 5. 后续与未决事项

可选。列出待验证项、遗留风险、下一步动作；没有就删除本节。
```

## 写作规则

- 只写本次会话中实际执行、实际验证过的事实；命令和输出必须真实，不推测、不补全。
- 结论先行；摘要超过 5 行说明还没想清楚。
- 对比表是核心，宁可少写背景，也不要把对比写成走过场。
- 用绝对日期，不用「今天 / 上周」。
- 不确定的内容标注「待确认」，不要写成结论。
- 术语保留英文原文（UEFI、`grub.cfg`、`fs_uuid` 等），中文解释一次即可。
- 不写无证据的评价（「大幅提升」「更稳定」），要写可观察的指标或现象。
- 不复制整段日志，只引用支撑结论的关键几行。
- 篇幅通常 60–150 行；长内容按主题拆篇。

## 执行流程

1. 确认范围：哪些操作、哪个决策需要沉淀。
2. 从对话中提取：目标、约束、实际执行的命令、验证证据、最终决定、被否决的方案。
3. 检查目标目录结构，确定路径与版本号。
4. 按模板写入文件。
5. 回报：文件路径 + 三行摘要；有未决事项时单独列出。

## 交付检查

- [ ] 结论摘要能让没参与的人 30 秒内知道结果
- [ ] 对比表至少两个方案，且理由可验证
- [ ] 日期、版本、状态齐全
- [ ] 没有编造的命令或输出
- [ ] 路径符合 note 目录现有约定
